\section{Executive Summary}

This project compares a relational database management system and a graph database using the same dataset of AI-related research papers collected from OpenAlex.
The relational implementation uses PostgreSQL, while the graph implementation uses Neo4j.

The main objective is not only to check which system is faster, but also to understand how each system represents and queries relationship-heavy scholarly data.
Scientific papers naturally form a graph: authors write papers, papers cite other papers, papers have topics, and authors become connected through shared publications, topics, and citations.

The work completed so far includes:

\begin{itemize}
    \item collecting and cleaning an OpenAlex subset focused on AI, Machine Learning, Large Language Models, and Retrieval-Augmented Generation;
    \item modeling the same data in PostgreSQL and Neo4j;
    \item loading both databases with the same CSV files;
    \item validating that both databases contain matching entity and relationship counts;
    \item writing equivalent SQL and Cypher queries;
    \item benchmarking 11 query pairs;
    \item generating charts and tables for presentation.
\end{itemize}

The current benchmark shows that PostgreSQL is faster on most queries for this small dataset, especially ranking and aggregation queries.
Neo4j is faster on the author citation network query, where the traversal follows a natural author-to-paper-to-paper-to-author graph pattern.
The broader conclusion is that PostgreSQL is very efficient for tabular analysis, while Neo4j is often clearer and more direct for graph-shaped questions.

\section{Project Goal and Research Questions}

The goal of the project is to compare PostgreSQL and Neo4j on the same AI research paper dataset.
The comparison focuses on data modeling, query complexity, expressiveness, execution time, and suitability for relationship-heavy analysis.

The main research questions are:

\begin{enumerate}
    \item How can the same scholarly dataset be modeled in a relational database and in a graph database?
    \item Which system makes common analytical queries easier to express?
    \item Which system performs better on the selected dataset and query workload?
    \item Are graph-shaped queries more naturally represented in Neo4j than in PostgreSQL?
    \item What are the practical trade-offs between relational joins and graph traversals?
\end{enumerate}

\section{Data Collection and Cleaning Pipeline}

The collection script is \texttt{src/collect\_openalex.py}.
It uses only the Python standard library so the project can run without dependency installation.

The pipeline performs the following operations:

\begin{enumerate}
    \item Calls the OpenAlex Works API using AI-related search terms.
    \item Uses cursor pagination to retrieve multiple pages of results.
    \item Saves raw API objects as JSONL.
    \item Reconstructs abstracts from OpenAlex abstract inverted indexes when available.
    \item Extracts paper metadata such as title, year, DOI, OpenAlex ID, citation count, and matched search terms.
    \item Extracts authors and paper-author relationships.
    \item Extracts topics and paper-topic relationships.
    \item Extracts citations where both the citing and cited papers are inside the selected subset.
    \item Removes duplicate paper-author pairs before database loading.
    \item Writes normalized CSV files for both PostgreSQL and Neo4j.
\end{enumerate}

\subsection{Data Quality Issue}

During PostgreSQL loading, the project found that OpenAlex can contain duplicate author entries for the same paper.
This produced a duplicate primary key error in the \texttt{paper\_authors} table.

The fix was to de-duplicate paper-author relationships by \texttt{(paper\_id, author\_id)} during normalization.
This is a useful project detail because it shows a realistic data cleaning problem and how it was solved.

\section{PostgreSQL Relational Model}

PostgreSQL uses a normalized relational schema.
Entities are represented as tables, and many-to-many relationships are represented as bridge tables.

\begin{table}[h]
\centering
\caption{PostgreSQL tables}
\label{tab:postgres-schema}
\begin{tabular}{|p{0.24\textwidth}|p{0.62\textwidth}|}
\hline
\textbf{Table} & \textbf{Purpose} \\
\hline
\texttt{papers} & Stores paper metadata such as title, year, DOI, abstract, topic, citation count, and OpenAlex URL. \\
\hline
\texttt{authors} & Stores author IDs and display names. \\
\hline
\texttt{topics} & Stores topic IDs and names. \\
\hline
\texttt{paper\_authors} & Bridge table connecting papers and authors. \\
\hline
\texttt{paper\_topics} & Bridge table connecting papers and topics. \\
\hline
\texttt{citations} & Stores directed paper-to-paper citation links. \\
\hline
\end{tabular}
\end{table}

This model is strong for:

\begin{itemize}
    \item aggregations;
    \item filtering;
    \item sorting;
    \item structured joins;
    \item enforcing primary and foreign keys.
\end{itemize}

However, graph-shaped questions can become verbose because they require multiple joins or recursive queries.

\section{Neo4j Graph Model}

Neo4j uses nodes and relationships.
This representation is closer to the natural structure of scholarly data.

\begin{table}[h]
\centering
\caption{Neo4j graph model}
\label{tab:neo4j-model}
\small
\begin{tabular}{|p{0.30\textwidth}|p{0.56\textwidth}|}
\hline
\textbf{Graph element} & \textbf{Meaning} \\
\hline
\texttt{(:Paper)} & Research paper node. \\
\hline
\texttt{(:Author)} & Author node. \\
\hline
\texttt{(:Topic)} & Topic node. \\
\hline
Author \(\rightarrow\) Paper & Authorship relationship, implemented as \texttt{AUTHORED}. \\
\hline
Paper \(\rightarrow\) Topic & Topic assignment relationship, implemented as \texttt{HAS\_TOPIC}. \\
\hline
Paper \(\rightarrow\) Paper & Directed citation relationship, implemented as \texttt{CITES}. \\
\hline
\end{tabular}
\normalsize
\end{table}

Example graph patterns:

\begin{verbatim}
(Author)-[:AUTHORED]->(Paper)
(Paper)-[:HAS_TOPIC]->(Topic)
(Paper)-[:CITES]->(Paper)
\end{verbatim}

This model is strong for:

\begin{itemize}
    \item citation paths;
    \item author collaboration;
    \item shared topics;
    \item author citation networks;
    \item relationship traversal.
\end{itemize}

\section{Example of Equivalent SQL and Cypher}

The benchmark pairs each analytical question with one SQL query and one Cypher query.
The goal is not to make the queries textually identical, but to make them answer the same logical question over the same loaded data.

One representative example is the author citation network query.
The question is: \textit{which authors are connected because one author's paper cites another author's paper?}

In Neo4j, the graph path is written directly:

\begin{verbatim}
MATCH (source:Author)-[:AUTHORED]->(:Paper)-[:CITES]->(:Paper)
      <-[:AUTHORED]-(target:Author)
WHERE source.author_id <> target.author_id
RETURN source.display_name AS citing_author,
       target.display_name AS cited_author,
       count(*) AS citation_edges
ORDER BY citation_edges DESC
LIMIT 10;
\end{verbatim}

The equivalent SQL query follows the same logical path using joins:

\begin{verbatim}
SELECT
    source_author.display_name AS citing_author,
    target_author.display_name AS cited_author,
    COUNT(*) AS citation_edges
FROM paper_authors source_pa
JOIN citations c ON c.citing_paper_id = source_pa.paper_id
JOIN paper_authors target_pa ON target_pa.paper_id = c.cited_paper_id
JOIN authors source_author ON source_author.author_id = source_pa.author_id
JOIN authors target_author ON target_author.author_id = target_pa.author_id
WHERE source_pa.author_id <> target_pa.author_id
GROUP BY source_author.author_id, source_author.display_name,
         target_author.author_id, target_author.display_name
ORDER BY citation_edges DESC
LIMIT 10;
\end{verbatim}

This example shows the main modeling difference.
In Neo4j, the query is shaped like the relationship path.
In PostgreSQL, the same path is reconstructed through relational joins.

\section{Benchmark Methodology}

The benchmark is run with:

\begin{verbatim}
python src/benchmark_queries.py --runs 5 --warmups 1
\end{verbatim}

The methodology is:

\begin{itemize}
    \item one warmup run per query/system pair;
    \item five measured runs per query/system pair;
    \item PostgreSQL timing uses \texttt{EXPLAIN (ANALYZE, FORMAT JSON)};
    \item Neo4j timing uses \texttt{PROFILE} through \texttt{cypher-shell --format verbose};
    \item raw results are saved in \texttt{benchmarks/results/benchmark\_results.csv};
    \item Markdown results are saved in \texttt{docs/benchmark\_results.md}.
\end{itemize}

This benchmark should be interpreted as a local project benchmark, not as a universal ranking of PostgreSQL and Neo4j.
Performance depends on data size, indexing, cache state, hardware, and query shape.

Values above 1x mean Neo4j was slower than PostgreSQL; values below 1x mean Neo4j was faster.

\section{Interpretation}

The benchmark has three important interpretations.

\subsection{PostgreSQL is strong for tabular aggregation}

Queries such as most cited papers, most frequent topics, and citation links are very efficient in PostgreSQL.
These queries match the strengths of a relational DBMS: indexes, joins, grouping, and ordering.

\subsection{Neo4j is clearer for graph-shaped questions}

Neo4j's Cypher syntax is often easier to read when the question is naturally expressed as a path.
For example, an author citation network can be expressed as:

\begin{verbatim}
(Author)-[:AUTHORED]->(Paper)-[:CITES]->(Paper)<-[:AUTHORED]-(Author)
\end{verbatim}

In PostgreSQL, the same query requires several joins across \texttt{paper\_authors}, \texttt{citations}, and \texttt{authors}.

\subsection{The result depends on dataset size and query shape}

The current dataset is intentionally small.
Therefore, the results should not be interpreted as a general statement that PostgreSQL is always faster.
With larger graphs, deeper traversals, more complex path search, or additional graph indexes/projections, the comparison could change.

\subsection{Relational Joins vs Graph Traversal}

One of the central course ideas is that relationship-heavy data can be handled in different ways.
In a relational DBMS, a relationship is normally reconstructed at query time using joins.
In a graph DBMS, a relationship is stored as a first-class edge and can be traversed directly.

Our project demonstrates this difference with citation and authorship data.
For example, the author citation network query has the following logical structure:

\begin{verbatim}
Author -> Paper -> Cited Paper -> Author
\end{verbatim}

In PostgreSQL, this path is rebuilt by joining \texttt{paper\_authors}, \texttt{citations}, and \texttt{authors}.
In Neo4j, the same path is expressed directly in Cypher.
This is why the project is a practical example of the lecture distinction between relationships-as-joins and relationships-as-edges.

\subsection{Why RDF and Data Warehousing Were Not Used}

The course also covers RDF databases and data warehousing.
Those topics are related to data management, but they are not the project model we selected.

RDF represents data as triples and is useful for semantic web and ontology-oriented data.
Our implementation uses Neo4j's property graph model instead, because the approved project topic was a DBMS comparison between a relational database and a graph database.

Data warehousing focuses on analytical schemas such as star schemas and OLAP analysis.
Our project is not a data warehouse project: we did not design a fact table, dimensions, or OLAP sessions.
Instead, we compare PostgreSQL and Neo4j on the same operational/analytical OpenAlex subset.
This distinction is important because the evaluation criteria are different.

\section{Main Findings}

\begin{itemize}
    \item The same OpenAlex dataset was successfully represented in both PostgreSQL and Neo4j.
    \item PostgreSQL and Neo4j were loaded with matching entity and relationship counts.
    \item PostgreSQL was faster on 10 out of 11 benchmarked queries.
    \item Neo4j was faster on the author citation network query.
    \item Neo4j query syntax is often more natural for relationship traversal.
    \item PostgreSQL is highly efficient for relational aggregation and sorting.
    \item The most useful comparison is not only speed, but also modeling clarity and query expressiveness.
\end{itemize}

\section{Limitations}

\begin{itemize}
    \item The dataset is a selected subset, not the full OpenAlex dataset.
    \item Benchmark results were produced on a local machine and depend on local hardware.
    \item Only 11 queries were benchmarked.
    \item The benchmark focuses on server-reported query time, not full application-level latency.
    \item The Neo4j model uses the basic graph database; advanced graph data science projections were not used.
\end{itemize}

\section{Conclusion}

This project demonstrates a practical comparison between PostgreSQL and Neo4j using AI research paper data from OpenAlex.
The relational model is efficient and structured, while the graph model is expressive and natural for relationship-heavy analysis.

The current results show PostgreSQL as faster for most queries on the small benchmark dataset, but Neo4j provides clearer graph traversal semantics and outperforms PostgreSQL on the author citation network query.
This supports a balanced conclusion: PostgreSQL is a strong choice for structured analytical workloads, while Neo4j becomes especially valuable when the main questions are about relationships, paths, and networks.
