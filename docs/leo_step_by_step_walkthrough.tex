\section{What the Project Is About}

The project is a DBMS comparison.
We compare:

\begin{itemize}
    \item \textbf{PostgreSQL 16}: a relational database, based on tables and SQL;
    \item \textbf{Neo4j 5}: a graph database, based on nodes, relationships, and Cypher.
\end{itemize}

The dataset is about AI research papers from OpenAlex.
This is a good dataset because research papers naturally have many relationships:

\begin{itemize}
    \item authors write papers;
    \item papers have topics;
    \item papers cite other papers;
    \item authors can be connected through citations, shared papers, or shared topics.
\end{itemize}

This makes it suitable for comparing a relational model and a graph model.

\subsection{The Core Difference: Joins vs Traversal}

The main conceptual difference is this:

\begin{itemize}
    \item In PostgreSQL, relationships are reconstructed by joining tables.
    \item In Neo4j, relationships are stored directly as edges and traversed as paths.
\end{itemize}

Example:

\begin{quote}
Which authors are connected because one author's paper cites another author's paper?
\end{quote}

In PostgreSQL, we need several joins between \texttt{paper\_authors}, \texttt{citations}, and \texttt{authors}.
In Neo4j, we write the relationship as a path:

\begin{verbatim}
(Author)-[:AUTHORED]->(Paper)-[:CITES]->(Paper)<-[:AUTHORED]-(Author)
\end{verbatim}

This is the central reason our project is meaningful.
The same real-world question can be represented in two different database models.

\section{The Full Project Pipeline}

The full pipeline is:

\begin{verbatim}
OpenAlex API
  -> raw JSONL records
  -> cleaned normalized CSV files
  -> PostgreSQL relational tables
  -> Neo4j graph nodes and relationships
  -> equivalent SQL and Cypher queries
  -> benchmark results
  -> charts, report, and presentation
\end{verbatim}

Every step has a reason:

\begin{itemize}
    \item We use OpenAlex because it gives real academic data.
    \item We save raw JSONL so the original API records are preserved.
    \item We produce CSV files because both databases can load the same files.
    \item We load the same logical data into PostgreSQL and Neo4j so the comparison is fair.
    \item We write equivalent queries so each system answers the same question.
    \item We benchmark execution time to compare behavior, not only syntax.
    \item We create a report and slides so the project can be explained from requirements to conclusions.
\end{itemize}

The most important fairness principle is:

\begin{quote}
Both PostgreSQL and Neo4j must receive the same cleaned dataset.
Otherwise, the comparison would not be valid.
\end{quote}

\section{Step 2: Cleaning and Normalizing the Data}

OpenAlex data is nested.
For example, a paper object can contain authors, topics, citations, abstract information, and metadata all inside one JSON object.

Databases are easier to load if the data is normalized into separate CSV files.
So the script creates:

\begin{verbatim}
data/processed/papers.csv
data/processed/authors.csv
data/processed/topics.csv
data/processed/paper_authors.csv
data/processed/paper_topics.csv
data/processed/citations.csv
\end{verbatim}

\subsection{Important Cleaning Problems}

We solved these problems:

\begin{itemize}
    \item \textbf{Nested JSON}: converted into flat CSV files.
    \item \textbf{Abstract inverted index}: reconstructed abstracts into readable text.
    \item \textbf{Duplicate relationships}: removed duplicate paper-author pairs.
    \item \textbf{External citations}: kept only citations where both papers exist in our selected subset.
\end{itemize}

This step is important because it is the ETL part of the project:

\begin{verbatim}
Extract: OpenAlex API
Transform: clean and normalize JSON
Load: import CSV files into PostgreSQL and Neo4j
\end{verbatim}

\subsection{Why We Did Not Load the Raw JSON Directly}

OpenAlex records are rich but messy for direct database comparison.
A single work can contain nested authorships, nested topics, abstract information, IDs, URLs, citation references, and metadata.
If we loaded this raw structure directly into only one database, the comparison would become unfair and hard to explain.

Instead, we normalized the information into a shared tabular format first.
This gives us one clean intermediate dataset.
Then both PostgreSQL and Neo4j are loaded from that same intermediate dataset.

This is important because it separates two concerns:

\begin{itemize}
    \item \textbf{Data preparation}: done once in Python.
    \item \textbf{Database comparison}: done after both databases contain the same cleaned data.
\end{itemize}

\subsection{Important ETL Decisions}

\begin{table}[H]
\centering
\small
\begin{tabular}{|p{0.30\textwidth}|p{0.58\textwidth}|}

\end{table}

\subsection{What ``Normalize'' Means Here}

Normalization means splitting data into separate logical tables instead of repeating everything inside one huge table.
For example, if a paper has ten authors, we do not repeat the full paper row ten times.
Instead:

\begin{itemize}
    \item the paper appears once in \texttt{papers};
    \item each author appears once in \texttt{authors};
    \item the connections appear in \texttt{paper\_authors}.
\end{itemize}

This reduces duplication and makes relationships explicit.
It also prepares the data for PostgreSQL tables and Neo4j graph relationships.

\subsection{Primary Keys, Foreign Keys, and Indexes}

PostgreSQL uses primary keys to guarantee uniqueness.
For example, \texttt{papers.paper\_id} is the primary key of \texttt{papers}.
This means the same paper cannot be inserted twice with the same ID.

PostgreSQL uses foreign keys to guarantee valid relationships.
For example, \texttt{paper\_authors.paper\_id} references \texttt{papers.paper\_id}.
This prevents a relationship from pointing to a paper that does not exist.

Indexes are added on columns commonly used in filters, joins, or ordering:

\begin{itemize}
    \item \texttt{publication\_year}, useful for year filters;
    \item \texttt{cited\_by\_count}, useful for ranking papers by citation count;
    \item \texttt{author\_id}, useful for author joins;
    \item \texttt{topic\_id}, useful for topic joins;
    \item \texttt{cited\_paper\_id}, useful for citation lookup.
\end{itemize}

This connects to the course topic of file organization and access paths:
the DBMS can use indexes to avoid scanning everything when a faster lookup is available.

\subsection{How PostgreSQL Represents Relationships}

PostgreSQL does not store graph edges directly.
It represents relationships through rows in tables.

Example:

\begin{verbatim}
papers.paper_id
authors.author_id
paper_authors(paper_id, author_id)
\end{verbatim}

To find which authors wrote which papers, SQL joins these tables.
This is powerful and standard, but relationship-heavy queries can become long because every relationship must be reconstructed from tables.

\section{Step 6: Neo4j Implementation}

Neo4j uses a graph model.
That means data is stored as nodes and relationships.

Nodes:

\begin{itemize}
    \item \texttt{Paper};
    \item \texttt{Author};
    \item \texttt{Topic}.
\end{itemize}

Relationships:

\begin{itemize}
    \item \texttt{(Author)-[:AUTHORED]->(Paper)};
    \item \texttt{(Paper)-[:HAS\_TOPIC]->(Topic)};
    \item \texttt{(Paper)-[:CITES]->(Paper)}.
\end{itemize}

\subsection{Why This Graph Model Fits OpenAlex}

OpenAlex data is naturally graph-shaped.
The main objects are papers, authors, and topics.
The most interesting information is often not inside one object, but between objects:

\begin{itemize}
    \item which author wrote which paper;
    \item which paper belongs to which topic;
    \item which paper cites another paper;
    \item which authors are connected through citations or shared topics.
\end{itemize}

Neo4j stores these connections directly.
That makes path questions easier to express.
For example, a citation network question can be written as a readable chain of nodes and relationships.

\subsection{Neo4j Labels, Properties, and Constraints}

In Neo4j:

\begin{itemize}
    \item \textbf{labels} classify nodes, such as \texttt{Paper}, \texttt{Author}, and \texttt{Topic};
    \item \textbf{properties} store values, such as title, display name, year, and citation count;
    \item \textbf{relationships} connect nodes, such as \texttt{AUTHORED}, \texttt{HAS\_TOPIC}, and \texttt{CITES}.
\end{itemize}

We also define uniqueness constraints:

\begin{itemize}
    \item every \texttt{Paper} has a unique \texttt{paper\_id};
    \item every \texttt{Author} has a unique \texttt{author\_id};
    \item every \texttt{Topic} has a unique \texttt{topic\_id}.
\end{itemize}

These constraints play a similar role to primary keys in PostgreSQL.
They make importing safer and make node lookup more efficient.

\subsection{How Neo4j Represents Relationships}

In Neo4j, the relationship is part of the stored model.
For example:

\begin{verbatim}
(a:Author)-[:AUTHORED]->(p:Paper)
\end{verbatim}

This directly means:

\begin{quote}
Author \texttt{a} wrote paper \texttt{p}.
\end{quote}

We do not need a bridge table in Neo4j.
The edge itself is the relationship.
This is why Neo4j is easier to read for path-based questions.

\subsection{What ``Equivalent Query'' Means}

Equivalent does not mean the SQL and Cypher text look identical.
They cannot look identical because the data models are different.
Equivalent means:

\begin{quote}
Both queries answer the same logical question over the same data.
\end{quote}

For example, PostgreSQL may need five joined tables while Neo4j needs one path pattern.
That is acceptable because each query uses the natural language of its DBMS.
The important thing is that the result meaning is the same.

\subsection{Example Query}

Question:

\begin{quote}
Which authors are connected because one author's paper cites another author's paper?
\end{quote}

In Neo4j, this is naturally written as a graph path:

\begin{verbatim}
(Author)-[:AUTHORED]->(Paper)-[:CITES]->(Paper)<-[:AUTHORED]-(Author)
\end{verbatim}

In PostgreSQL, the same idea requires joining multiple tables:

\begin{itemize}
    \item \texttt{paper\_authors};
    \item \texttt{citations};
    \item \texttt{authors}.
\end{itemize}

This is one of the main differences between the two systems.

\section{Step 9: Benchmarking}

The benchmark script is:

\begin{verbatim}
src/benchmark_queries.py
\end{verbatim}

We run:

\begin{verbatim}
python src/benchmark_queries.py --runs 5 --warmups 1
\end{verbatim}

Benchmark method:

\begin{itemize}
    \item 1 warmup run per query/system;
    \item 5 measured runs per query/system;
    \item PostgreSQL measured with \texttt{EXPLAIN ANALYZE};
    \item Neo4j measured with \texttt{PROFILE};
    \item raw results saved as CSV.
\end{itemize}

Results are saved in:

\begin{verbatim}
benchmarks/results/benchmark_results.csv
docs/benchmark_results.md
\end{verbatim}

\subsection{Why We Use Warmups and Averages}

One query execution time can be noisy.
The computer may be busy, the database may be loading metadata, or some data may already be cached in memory.
To reduce random effects, the benchmark uses:

\begin{itemize}
    \item warmup runs, which are ignored;
    \item multiple measured runs;
    \item average time for comparison.
\end{itemize}

This does not make the benchmark perfect, but it makes it more reliable than running each query once manually.

\subsection{Why PostgreSQL Uses EXPLAIN ANALYZE}

\texttt{EXPLAIN ANALYZE} runs the SQL query and reports the execution time and query plan.
The query plan is the DBMS's internal strategy, such as:

\begin{itemize}
    \item scan a table;
    \item use an index;
    \item join tables;
    \item group rows;
    \item sort results.
\end{itemize}

This connects directly to the course topic of query processing.
The DBMS does not simply ``read SQL'' line by line.
It builds an execution plan and chooses physical operators.

\subsection{Why Neo4j Uses PROFILE}

\texttt{PROFILE} runs the Cypher query and shows the graph execution plan.
It can show operations such as:

\begin{itemize}
    \item find nodes by label or index;
    \item expand relationships;
    \item filter paths;
    \item aggregate results;
    \item sort and limit output.
\end{itemize}

This is the graph equivalent of looking at how the database executes the query internally.

\subsection{What the Benchmark Does Not Prove}

The benchmark is useful, but it should be interpreted carefully.
It does not prove that PostgreSQL is always better than Neo4j.
It proves that, for our current dataset, machine, indexes, and query set, PostgreSQL was faster on most measured queries and Neo4j was faster on the author citation network query.

Important limitations:

\begin{itemize}
    \item the dataset is a small OpenAlex subset, not the full OpenAlex database;
    \item the benchmark runs locally, not on a production server;
    \item both systems are containerized through Docker;
    \item query performance can change with more data, different indexes, or different query patterns;
    \item Neo4j may become more useful for deeper graph traversal and interactive network exploration.
\end{itemize}

\subsection{Lecture Concepts Explained Without the Slides}

\textbf{Graph databases.}
The graph database lecture explains that some data is naturally represented as a network.
In a network, the connections are first-class information.
Our project uses this idea because OpenAlex papers are connected to authors, topics, and other papers.

\textbf{Neo4j property graph.}
Neo4j uses the property graph model.
This means nodes and relationships can both have properties.
For our project:

\begin{itemize}
    \item \texttt{Paper} nodes have title, year, DOI, citation count, abstract, and topic properties;
    \item \texttt{Author} nodes have author ID and display name;
    \item \texttt{Topic} nodes have topic ID and display name;
    \item \texttt{AUTHORED} relationships can store author position and corresponding-author information;
    \item \texttt{HAS\_TOPIC} relationships can store topic score and source;
    \item \texttt{CITES} relationships connect one paper to another.
\end{itemize}

\textbf{Cypher pattern matching.}
Cypher queries use patterns.
A pattern visually resembles the graph itself.
For example:

\begin{verbatim}
MATCH (a:Author)-[:AUTHORED]->(p:Paper)
RETURN a.display_name, p.title
\end{verbatim}

This reads almost like:

\begin{quote}
Find authors connected by an AUTHORED relationship to papers.
\end{quote}

\textbf{Relational joins.}
In relational databases, relationships are represented by values in tables.
To answer relationship questions, SQL joins tables using matching IDs.
For example, joining \texttt{paper\_authors} with \texttt{authors} gives the names of authors for each paper.

\textbf{Query processing.}
The query processing lectures explain that a DBMS translates a query into an execution plan.
The execution plan may contain operators such as scan, selection, projection, join, grouping, sorting, and aggregation.
Our benchmark connects to this because PostgreSQL uses \texttt{EXPLAIN ANALYZE} and Neo4j uses \texttt{PROFILE}.

\textbf{File organization and indexes.}
The file organization material explains that data access is not free.
The DBMS needs a way to find data efficiently.
Indexes help by creating faster access paths.
That is why our PostgreSQL schema defines indexes and our Neo4j schema defines uniqueness constraints.

\textbf{RDF databases.}
RDF stores data as triples: subject, predicate, object.
It is useful for semantic web, ontologies, and linked data.
We did not use RDF because our approved comparison is PostgreSQL versus Neo4j property graphs.

\textbf{Data warehousing.}
Data warehousing focuses on analytical schemas such as fact tables, dimension tables, star schemas, and OLAP.
We did not build a warehouse because our project is a DBMS comparison, not a dimensional modeling project.
This is important if the professor asks why there is no star schema.
